# FloorForge-AI Technical & Business Architecture Audit
**Date:** 2026-07-31 | **Status:** Early Stage | **Codebase Version:** 0.1.0

---

## Executive Summary

**FloorForge** is an early-stage autonomous hardwood floor refinishing operating system positioned as a Robot-as-a-Service (RaaS) platform. The current codebase (v0.1.0) is a **concept validation and pilot recruitment site**, not a production system. It excels in:

- **Honest positioning:** Marketing site explicitly labels all technical figures as design targets, not measured results
- **Architectural clarity:** Five concept robot platforms (Sander D1, Edger E1, Coater C1, Layer L1, Scanner S1) with clearly defined roles, coverage patterns, and telemetry requirements
- **Pilot readiness:** Clear conversion funnel, transparent ROI model, scripted demo assistant, and dashboard mockup
- **Modular design:** Modern Next.js/TypeScript stack with Zustand state management and WebGL-based 3D simulators

**Overall Maturity: Pre-MVP (Pilot Planning Phase)**
- ✅ Hardware concept platforms fully specced
- ✅ Marketing/waitlist funnel live
- ❌ No production backend API
- ❌ No real hardware deployments
- ❌ No measured customer data or logistics
- ⚠️ Supabase schema documented but not implemented

### Architecture Patterns

#### 1. **Graceful Degradation**
The codebase is designed to work with **zero environment variables**:
- Clerk auth disabled → site still loads, `/dashboard` accessible
- Supabase not configured → `getSupabase()` returns `null`
- Formspree form ID missing → waitlist CTA falls back to `mailto:`

**Code example:** `lib/supabase/client.ts`
```typescript
export function getSupabase(): SupabaseClient | null {
  if (!url || !key) return null; // Safe fallback
  // ...
}
```

#### 2. **Modular Component Design**
```
components/
├── simulator/        # 3D visualization (FloorScene, RobotMesh, etc.)
├── ui/              # Atomic primitives (Button, Dialog, etc.)
├── Chatbot.tsx      # Scripted demo assistant
├── ROICalculator.tsx # Interactive financial model
├── WaitlistCTA.tsx  # Form submission handler
└── Header.tsx       # Navigation & auth UI
```

Each component is:
- **Single-responsibility:** One feature or UI concept
- **Isolated state:** Uses Zustand for scene state, hooks for form state
- **Reusable:** No hardcoded job context, renders same across pages

#### 3. **Simulator Architecture**

The simulator layer is a **stateful scene orchestrator** using a custom Zustand store (`useSim`):

**State tree:**
```typescript
interface SimState {
  selectedId: string;        // Active robot: "sand", "edge", "coat", "lay", "scan"
  roomW, roomL: number;      // Room dimensions (metres)
  running: boolean;          // Playback state
  speed: number;             // 1x–30x playback multiplier
  metrics: SimMetrics;       // Live coverage, ETA, dust (mock)
  resetToken: number;        // Force scene rebuild on job change
  exploded: number;          // 0–1 (0% to 100% exploded view)
  cutaway: boolean;          // Show machine internals (cutaway)
  cameraMode: "orbit" | "follow" | "top";
}
```

**Data flow:**
1. User selects robot → `select(id)` → `resetToken` bumped
2. Scene detects token change → calls `planPath()` to compute coverage waypoints
3. FloorScene renders floor + robot; robot animates along waypoints
4. Metrics update as coverage progresses (mocked: `SimMetrics.coveragePct`)
5. HUD displays real-time ETA based on coverage rate

#### 4. **Path Planning**

Two coverage algorithms implemented in `lib/pathPlanning.ts`:

**Boustrophedon (ox-plough pattern):**
- Used by: Sander (D1), Coater (C1), Layer (L1), Scanner (S1)
- Algorithm: Parallel lanes spaced by working width, alternating direction
- Coverage: Minimizes total travel distance

**Perimeter (concentric rings):**
- Used by: Edger (E1) only
- Algorithm: Inward rings from room boundary
- Coverage: Efficient edge-only coverage

**Code quality:** Clean, textbook implementations with vector math and proper margin handling.

### Rendering Pipeline

**Three.js scene setup (`components/simulator/FloorScene.tsx`):**
1. **Environment:** Ambient light, directional shadow-casting light
2. **Floor:** Plane geometry, dynamic texture based on robot type (shows coverage as color)
3. **Robot:** Exported 3D model (gltf/glb), animated along waypoints
4. **Dust particles:** (Optional) Procedural particle effect during sanding
5. **Camera:** Three modes (orbit, follow, top-down)

**Performance considerations:**
- WebGL 1 fallback available (detected at runtime)
- Responsive canvas: scales to viewport
- Texture reuse: Single floor material, shader-based color animation
- No memory leaks on unmount (cleanup in effect)

## 4. CNC and Workflow Telemetry Architecture

### Telemetry Design (Pre-Implementation)

The dashboard and simulator reveal the **intended** telemetry schema. Real hardware will log:

#### Job-Level Telemetry
| Field | Type | Source | Example |
|-------|------|--------|---------|
| `job_id` | UUID | Dispatch → Job record | `rf-2847` |
| `site_name` | string | GC/customer input | "Meridian Tower, Fl. 12-18" |
| `sqft` | number | LiDAR scan | 12500 |
| `robot_id` | string | Fleet registry | "FF-03A" |
| `status` | enum | Job state machine | "in_progress", "paused", "complete", "failed" |
| `start_time`, `end_time` | timestamp | Robot clock | ISO 8601 |

#### Per-Pass (Multi-Grit) Telemetry
| Field | Type | Range | Notes |
|-------|------|-------|-------|
| `pass_number` | int | 1–4 | 36, 80, 120, 180 for sanding |
| `grit_tag` | string | "36", "Seal", "Finish" | Display label |
| `coverage_pct` | float | 0–100 | % of floor area processed |
| `coverage_area_m2` | float | 0–sqft | Cumulative coverage |
| `duration_sec` | int | Varies | Actual pass time |
| `average_speed_mps` | float | 0.15–0.6 | Robot ground speed |

#### Dust & Environmental Telemetry
| Field | Type | Unit | Target |
|-------|------|------|--------|
| `dust_reading_ugm3` | float | µg/m³ | < 15 (87% below OSHA action level) |
| `dust_sample_count` | int | count | Per 5-min interval |
| `hepa_filter_loading` | float | % | Track for maintenance scheduling |
| `ambient_temp` | float | °C | Pre/post cure window check |
| `ambient_humidity` | float | % | Finish curing conditions |

#### Finish Application Telemetry
| Field | Type | Unit | Target |
|-------|------|------|--------|
| `film_build_µm` | float | µm | ±5% of target |
| `application_speed` | float | m/s | Consistent 0.35 m/s target |
| `passes` | int | count | Seal (1) + finish (1–2) |
| `dry_time_hours` | float | h | Full cure logged |
| `sheen_reading` | float | gloss units | 60° gloss meter |

#### Quality & Pass/Fail
| Field | Type | Logic | Example |
|-------|------|-------|---------|
| `first_pass_approval` | bool | Coverage ≥ 99.5% | `true` = job approved |
| `uniformity_score` | float | 0–100 | Vision + dust variance |
| `rework_reason` | string | enum | "dust_spike", "thin_film", "skip_detected" |

### Currently Implemented vs. Planned

**✅ Designed (UI mockups exist):**
- Dashboard job list with status, progress bar, ETA
- Metrics HUD: coverage %, area finished, time remaining
- Fleet health table: robot uptime, health %, current job
- Analytics tab: first-pass approval %, dust avg, finish uniformity score

**⚠️ Partially implemented (simulator only):**
- SimMetrics struct (in-memory, mocked)
- Coverage calculation (simulated, based on speed + job ETA)
- Elapsed time tracking (wall-clock during playback)

**❌ Not implemented:**
- Supabase tables (schema comments only)
- Real hardware telemetry collection
- Data transmission from robot to server
- Webhook or real-time sync
- Per-job report generation
- Trend analytics (30-day rolling metrics)
- Alert thresholds (dust spike, coverage gap, finish failure)

### Telemetry Pipeline (Proposed)

```
Hardware (Robot) 
  ↓
  └─→ On-board logger (edge compute)
      ├─→ Real-time metrics (10 Hz dust, 1 Hz coverage)
      ├─→ Event log (pass start/end, error, pause)
      └─→ Video + flatness scan (background upload)
          ↓
          └─→ Gateway (WiFi/4G) to Supabase
              ├─→ Insert into jobs, sanding_reports, finish_applications
              ├─→ Trigger: Compute first-pass approval
              ├─→ Trigger: Generate QA map visualization
              └─→ Real-time Supabase subscriptions update dashboard
```

### Missing Telemetry Components

1. **Robot hardware:** No logging code, edge-compute, or radio uplink
2. **Gateway/API:** No `/api/jobs/{id}/telemetry` endpoint
3. **Data ingestion:** No message queue (Kafka/Bull), event streaming
4. **Validation layer:** No schema validation, data quality checks
5. **Alerting:** No threshold logic for anomalies (dust spike, coverage gap)
6. **Historical reporting:** No job summary generation, PDF export
7. **Customer API:** No data export for GCs, no webhook for integrations

## 6. Technical Debt Inventory

### Critical (Must Address Before Production)

#### 1. No API Layer
- **Risk:** Dashboard can't fetch real job data
- **Impact:** Multi-tenant isolation breaks; all users see same mock data
- **Work:** Design RESTful API (`/api/jobs`, `/api/robots`, `/api/telemetry`), add authentication middleware
- **Estimate:** 2–3 weeks (basic CRUD + auth)

#### 2. No Database Integration
- **Risk:** Data doesn't persist; users see hardcoded sample jobs
- **Impact:** Dashboard is non-functional for actual pilots
- **Work:** Write Supabase migrations, connect React components to real data, implement RLS policies
- **Estimate:** 2–3 weeks (schema + queries + permissions)

#### 3. No Authentication-Protected Job Data
- **Risk:** Pilot customer data exposed or missing entirely
- **Impact:** GDPR/compliance risk; multi-tenant isolation fails
- **Work:** Connect Clerk user ID to Supabase row-level security; test tenant isolation
- **Estimate:** 1 week

#### 4. No Test Suite
- **Risk:** Regressions on critical paths (simulator, ROI calc, coverage algorithm)
- **Impact:** Pilot deployment breaks due to untested changes
- **Work:** Add Jest/Vitest; test pathPlanning, ROI calc, simulator state transitions
- **Estimate:** 2–3 weeks (target 60%+ coverage on libs)

### High (Should Address in Next Sprint)

#### 5. No Payment/Subscription Logic
- **Risk:** Can't transition from free pilot to paid customer
- **Impact:** No revenue model executable
- **Work:** Add Stripe integration, subscription lifecycle, usage metering
- **Estimate:** 3–4 weeks (full billing cycle)

#### 6. No Real-Time Telemetry Ingestion
- **Risk:** Dashboard can't show live job updates
- **Impact:** Dashboard is read-only; customers see stale status
- **Work:** Design telemetry API, add Supabase real-time subscriptions, build webhook handler
- **Estimate:** 3–4 weeks (edge-to-cloud pipeline)

#### 7. No Error Handling or Observability
- **Risk:** Silent failures in production; no visibility into issues
- **Impact:** Pilot failures go undiagnosed; customer frustration
- **Work:** Add Sentry/Axiom, structured logging, error boundaries in React
- **Estimate:** 1–2 weeks

#### 8. No Performance Optimization
- **Risk:** Dashboard slow on poor connections; simulator stutters
- **Impact:** Poor customer experience during demos
- **Work:** Code-split components, lazy-load 3D assets, cache API responses
- **Estimate:** 1–2 weeks

### Medium (Nice to Have, Post-MVP)

#### 9. No Accessibility (a11y)
- **Current:** Some semantic HTML; no ARIA labels on dynamic content
- **Risk:** Exclude vision-impaired users; potential compliance issues
- **Work:** Audit with axe-core; add ARIA to simulator HUD, form labels
- **Estimate:** 1 week

#### 10. No Deployment Automation
- **Current:** Manual Vercel deployments (works, but no CI/CD)
- **Risk:** Inconsistent deployment, no rollback plan
- **Work:** Add GitHub Actions, preview environments, automated testing on PR
- **Estimate:** 1 week

#### 11. Pro Simulator (Pro Teardown) Incomplete
- **Current:** Placeholder `ProTeardown.tsx` references a Godot player (removed)
- **Risk:** "Launch Pro Simulator" button leads nowhere
- **Work:** Decide: WebGL native teardown (3D model + assembly explode) or video walkthrough

#### 12. Localization (i18n)
- **Current:** English only
- **Risk:** Can't expand to international markets (UK, Canada, Australia)

- **Estimate:** 1–2 weeks (initial setup; ongoing translations)

## 8. Risk Mitigation & Contingencies

### Technical Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| **Hardware prototype fails** | High | Pilot delayed 6–12 months | Start firmware NOW (parallel to web) |
| **Dust containment underperforms** | Medium | Liability, OSHA compliance | Test HEPA real-world (independent lab) |
| **Telemetry pipeline unreliable** | Medium | Customers can't verify results | Mock simulator first, unit tests |
| **Database scales poorly** | Low | Dashboard slow at 1000+ jobs | Use Supabase indexing, pagination; monitor query times |
| **Real-time subscriptions drop** | Medium | Customers see stale data | Fallback to 5s poll; implement reconnect logic |

### Business Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|-----------|
| **Pilot customers demand specs we can't deliver** | High | Scope creep, timeline slip | Lock scope in T&Cs; weekly syncs to manage expectations |
| **Competitors move faster** | Medium | Market share loss | Focus on differentiation: dust logging, data transparency |
| **Recruitment pool too small (not enough pilots)** | Low | Insufficient feedback | Expand target: facilities mgmt, GCs, not just contractors |
| **Insurance/liability roadblock** | Medium | Can't deploy in customer homes | Consult broker early; possibly limit to commercial sites first |

### Mitigation Strategy

1. **Assign clear owners** for each action item (not "team responsibility")
2. **Weekly sync:** Blockers, risks, scope changes
3. **Prototype early:** Don't wait for perfect API design; iterate based on feedback
4. **Customer advisory board:** 3–5 pilot customers in feedback loop from week 1
5. **Kill switch ready:** If hardware can't meet timeline, pivot to software licensing for existing contractors' robots

## 10. Appendices

### A. Technology Decision Rationale

**Why Next.js 16?**
- SSR + SSG support (future: static job report pages)
- Built-in API routes (fast path to MVP)
- Vercel deployment (zero DevOps for early stage)
- Typescript strict mode (catch bugs early)

**Why Zustand for state?**
- Lightweight (no Redux boilerplate)
- Hooks-based API (fits React 19)
- Excellent for decoupled simulator state

**Why Supabase, not custom PostgreSQL?**
- Managed backups, replication, security
- Real-time subscriptions (Postgres LISTEN/NOTIFY)
- Row-level security (multi-tenant isolation)
- Free tier covers pilot load

**Why Three.js for 3D?**
- Web standard (canvas + WebGL)
- Mature ecosystem
- React bindings (@react-three/fiber) mature
- Runs on mobile browsers (future: iPad field app)

- Throughput: ~2,200 sqft per robot per day
